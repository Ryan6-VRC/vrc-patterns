# color-adjust — hue/color slider on the shader's own property (Pattern, study)

Two ways to give a user a hue/color slider by driving a shader's own property directly (no HSV→RGB compute pass — out of scope here): lilToon's vec4 `_MainTexHSVG` (three sliders composed in one WD-ON Direct tree) and Poiyomi's scalar `_MainHueShift` (one slider, one tree).

**Provenance:** generalized from vendor costume color-adjust clips.

## Ground truth

The vec4-driving mechanism: under WD-ON an un-keyed channel reverts to the material default, and per-channel Override layers fight (each writes the whole vec4, last wins), so the fix is one WD-ON Direct tree in which each slider's 1D sub-tree writes only its own channel plus a constant `.w`. `BrokenDemo` is the counterexample kept for study. Pattern tier, no seam shipped: a consumer adapts in order — **`RepathClips` first** onto their own renderer (placeholder paths `Body`/`BodyBroken`), **then** pair `basis: avatar-root` with the MA merge component's `pathMode` per `_template`, or the repathed bindings land on the wrong node.

## Traps — Dependencies

The lilToon sliders require the target material to be lilToon (`_MainTexHSVG` is lilToon-only); `HueShift` requires Poiyomi (`_MainHueShift`). By-name property binding is inert — silently does nothing — on a renderer whose material is the wrong shader. **lilToon is necessary and not sufficient for Hue and Sat:** tone correction applies to the sampled `_MainTex` alone (`lil_common_frag.hlsl:312-317`) and `_Color` multiplies in after it (`:357`), so where the color lives in the `_Color` tint over a white or greyscale texture the RGB→HSV step sees saturation 0, the hue add and the saturation multiply are both inert, and the tint rides through untouched — Val is a straight brightness multiply and is the one leg that still works. The hue must live in the texture. Tone correction is then lerped through `_MainColorAdjustMask` (`:330-343`), so a mask passing little of the sheet leaves a correct install visibly inert — and rotating the hue of a near-black or near-white region does nothing at any mask coverage.

A second precondition on the same property: `_MainTexHSVG` is compiled out where `LIL_FEATURE_MAIN_TONE_CORRECTION` is undefined (`:315`), and **which mechanism defines it is the shader family.** Plain (`lts*`) takes the project-wide Shader Setting, on unless a narrowing pass cleared it. **Multi** (`ltsmulti*`) ignores shader settings altogether (`lil_common.hlsl:21`, via `LIL_IGNORE_SHADERSETTING`) and takes a per-material shader keyword instead, `EFFECT_HUE_VARIATION`, which lilToon writes on material save from `_MainTexHSVG != (0, 1, 1, 1) || _MainGradationStrength != 0` (`lilMaterialUtils.cs:450`) — so a Multi material stored at the **exact identity** with no gradation ships with the property absent from its variant, and all three sliders drive a uniform nothing reads. Store a non-identity HSVG; an offset too small to see suffices, since holding the keyword on is its only job, and a slider-neutral of `0` stays correct because the keyword follows the stored value, never the driven one.

**`ltsmulti_gem` is outside that fix**: the Gem branch clears `EFFECT_HUE_VARIATION` unconditionally (`:437`) and the shader declares no such variant, so no stored value makes these sliders work on `Hidden/lilToonMultiGem`.

**The build recomputes that keyword, but not on every path, which is what lets the emulator disagree with an upload.** `VRChatModule.OnPreprocessAvatar` runs `SetupMultiMaterial(materials, clips)`, whose clip scan enables the keyword from any `_MainTexHSVG` curve whatever the material stores — and the whole block early-returns for the `nadena.dev.ndmf.ApplyOnPlay` caller unless the project sets `isOptimizeInNDMF` (`VRChatModule.cs:61`). So an upload rescues an identity-stored Multi material and the play-mode build does not; storing the value is what makes the two agree. The plain family's counterpart is `SetupShaderSettingFromAnimationClip` (`lilToonSetting.cs:1329`), which keeps the project-wide feature on from any clip naming the property, no threshold — while `SetupShaderSettingFromMaterial` returns immediately for Lite and Multi names, so a Multi material never contributes to that setting either.

## Deriving `_MainColorAdjustMask` from the vendor's own colourways

On a garment whose colour is trim painted over a neutral sheet the mask is what keeps the sliders off the sheet, and the obvious instrument — cutting on the sheet's own saturation — fails on branding, since a vendor's gold logo and serial numbers are as saturated as the gold trim beside them and the slider ends up turning the manufacturer's name along with the garment. **Where the vendor ships that sheet in several colourways it has already answered the question: a pixel that varies across the set is what the vendor recolours, a pixel identical in all of them is fixed by intent** — the trim/decal split falls out of the definition instead of being tuned into a threshold.

Normalise each pixel's cross-colourway spread by its own brightness rather than by a global constant, or trim sitting in the sheet's baked shading varies by too few counts to clear the cut and fades out of the mask, leaving the trim to recolour unevenly by where the vendor happened to paint a highlight. Treat a bimodal spread histogram as the precondition rather than a formality — a sharp empty gap means the vendor recoloured by hue, and the cut is its midpoint, so no value in the gap needs revisiting when a sheet changes; a smeared one means a repaint, where this does not apply at all and a saturation threshold is the fallback that will take the decals with it. Smoothstep across that gap and dilate a few pixels rather than thresholding to binary, because tone correction is lerped through this mask (§Traps) — a hard edge bands along the trim, an undilated one leaves a bright seam against the sheet's own antialiasing — and import it as data, sRGB off, where it is sampled `.r` with `sampler_MainTex` (`lil_common_frag.hlsl:331`) and so inherits `_MainTex`'s wrap and filter with no sampler of its own.

## Behavior

`_MainTexHSVG` against a lilToon default of `(0, 1, 1, 1)`. To re-measure after an edit, read the renderer's `MaterialPropertyBlock`, not `sharedMaterial`, which stays at the authored value and reads as a false negative (`docs/verify.md`). **That read proves the write arrived, never that the shader consumes it** — under §Traps' compiled-out case the block holds the correct driven value while no pixel changes, so a Multi-family slider is verified by diffing renders of two positions and by nothing cheaper. A correct install with Hue=0.6, Sat=0.4, Val=0.9 yields `(0.6, 0.4, 0.9, 1.0)` — all three sliders take effect at once, no fight. The trap: `Broken_HueOnly_RevertsUnkeyed` (keys only `.x=1`) yields `(1, 1, 1, 1)` — the un-keyed `.y`/`.z`/`.w` took the **material default**; here the default happens to equal the intended hold so the damage is invisible, but on a material whose default differs (a pre-saturated body) the same clip would silently reset saturation.

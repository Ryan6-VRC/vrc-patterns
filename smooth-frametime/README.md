# smooth-frametime — frametime-aware, clean-settling float smoothing (Pattern, study)

Three float-smoothing constructions over one owned frametime rig: an exponential smoother in two α-flavours (`clamp01`, `remap`) and a constant-velocity **linear** smoother whose tapered step lands exactly on a static target. All are always-on cosmetic Direct-tree math, nothing synced or saved, so a consumer pays no synced bit. Pattern tier — lift the YAML and recompile with your own params/GUIDs; `built/` ships only so the graphs read in the animator window.

## Provenance

Generalized from standard VRChat DBT-math smoother constructions (vrc.school Advanced Blend Trees); the `IsLocal`-selected λ pair is a vendor outfit-smoother idiom (survey-verified; OSCmooth ships the same fork). The tapered linear lane is lifted from a private avatar's face-tracking smoothing layer. No real-avatar naming.

## Ground truth

The three outputs `SmoothedExpClamp` / `SmoothedExpRemap` / `SmoothedLinear` are AAPs; inputs are assumed in `[0,1]`. The λ pair and the linear lane's speed live in param **defaults**, so tuning them is an install-time edit with no tree surgery; the one exception is the linear lane's taper, which is a 1D key pair — a blend threshold is a compile-time constant, so retuning it is a YAML edit and a recompile. The exponential lanes are convex blends and cannot overshoot; the linear lane is an additive step over a clamped carry and holds `[0,1]` only while its taper rule (§Behavior) is met. Every weight is `≥0` by construction, so `blendtree-math`'s one hard `directWeight ≥ 0` constraint holds here for free. No seam and no dependencies: every clip writes an animator parameter, not a scene binding, so there is nothing to repath.

**The two-layer split (`Smooth/FrameTime` front-end, `Smooth/Smoothers`) is author-time legibility, not runtime structure.** Collapsing them into one Direct tree is mechanical — nest the children — and costs no timing, because layer order never bought same-frame data flow (`docs/gimmicks.md` "Layer order buys no same-frame data flow"). Fold it if you are counting layers. The rig is owned rather than borrowed from VRCFury's `FrameTimeService`, whose update-ordering contract is undocumented and fragile for a lifted entry.

## Traps

**Don't split λ reflexively.** `RateSelected` picks `rateLocal` or `rateRemote` by `IsLocal`, but both defaults ship **equal**. A split is warranted only when the two clients see genuinely different input — mostly OSC-driven params, where the wearer's client gets the immediate high-resolution update while remotes receive it capped to ~10 Hz at reduced resolution, so heavier remote smoothing masks that jitter. Absent that input asymmetry one λ is correct; the split exists as two editable defaults, not as shipped behavior.

**The crossover-weight hybrid this lane replaced does not hold a target at VRChat frame rates.** The earlier construction blended a constant-velocity far term with an exponential near term through a weight `W` computed from `|Δ|` against a crossover distance. `W` was a feed-forward chain of three AAPs (`Δ → |Δ| → crossover − |Δ| → W`), so it lagged the delta it gated by three frames; once one far step was wider than the band in which `W` reached full authority, the far term crossed the near zone every frame and the stale gate never closed. It settled at high frame rates and limit-cycled indefinitely on interior targets at VRChat's ordinary low ones, overshooting by one far step (`maxSpeed·FrameTime`) on every step at every rate. Widening the crossover restores the hold but keeps the overshoot and turns the landing exponential, which spends the linear feel the construction existed for. The lesson is general: a gate computed through a multi-hop AAP chain is stale by its depth, and a stability argument that assumes it is current is wrong at low frame rates. A consumer who lifted the old lane sees it as `SmoothedHybrid`; the rename to `SmoothedLinear` is deliberate, so that lifting the new YAML breaks loudly rather than changing behavior under the same name.

## Behavior

**`remap` is frametime-independent; `clamp01` is not.** `remap`'s steady-state decay ratio over a matched elapsed window holds constant across framerates; `clamp01` linearizes `1−e^(−x)` and so converges faster the larger the per-frame step (the lower the fps). `remap`'s independence holds only as far as its 1D keys sample the operating `RateStep` band densely — keep them dense where you drive it. `clamp01` is the cheaper, honestly framerate-dependent flavour when exact independence isn't needed.

**The linear lane moves at `maxSpeed` while it is farther than the taper from the target, then lands linearly to zero, with no overshoot and no residual.** Its step is `maxSpeed · FrameTime · clamp(Δ/taper, −1, 1)`, one 1D over the frame-start delta, so the only staleness is the one frame every computed AAP carries. That one frame is what sizes the taper: the landing rings around the target unless **`taper ≥ 4 · maxSpeed · dt_max`**, where `dt_max` is the longest frame the lane must survive — the recurrence's roots go complex above that ratio. Below the rule the lane rings and then decays (it still lands; the ringing amplitude grows with the shortfall, and a ring past 0 or 1 is the one case its AAP leaves `[0,1]`), so the failure is soft where the hybrid's was sustained. The shipped keys are sized for the shipped `maxSpeed` at a frame-rate floor the YAML comment names; `maxSpeed` is a param default and the taper is not, so **raising `maxSpeed` at install raises the floor in proportion — widen the keys with it.** Wider is the safe direction; its cost is a longer linear-to-zero tail, so settle time for a given step spreads across frame rates (slower at high fps, where the tail takes more frames) — closing that spread needs a delta that is not stale, which is a 2D lookup over target and state, not worth it for a cosmetic fade. `blendtree-math`'s linear smoother is this construction with the clamp band equal to one step, which is why it limit-cycles.

**Re-measuring after an edit.** Every blend param is read at frame start, so the feed-forward pipeline takes a few frames to fill after an input change. Host the built controller on a bare `Animator` and tick `Animator.Update(dt)` in edit mode — `docs/emulator.md` §"Pure controller math skips play mode entirely" owns the recipe. Measure more than one frame rate: the linear lane's claim is a frame-rate floor, and a single high-rate capture cannot falsify it.

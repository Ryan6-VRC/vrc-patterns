# object-sync — absolute world position + rotation for a droppable prop (Module)

A prop that can be set down anywhere in the world and is in the same place for everyone, including a player who joins after it was dropped: a two-stage contact measure quantizes its world transform on the wearer's client and `word-channel` replicates the bits, with no physbone, no Rigidbody, and no synced position of its own. The packaged novelty is the redundant fine stage — a second, bias-cancelling readout wide enough to absorb the coarse stage's error — which puts sub-millimetre placement anywhere in a ±4096 m world inside **28 synced bits** — a 27-bit transport wire plus the one enable bit — refreshed end to end in ~0.7 s.

Three built configurations ship, each with its own regenerated document, compiled controller and prefab, so a download is usable without this workspace: the entry root (one object, full rotation, 72 rotation bits on the wire), `y/` (one object, heading only, 24 rotation bits, the same 28 synced bits total) and `y_double/` (two objects, heading only, time-multiplexed onto one measure rig and ONE shared walk set, 29 synced bits: a 28-bit wire plus the shared enable). One build per avatar, whichever variant — all three share the parameter prefix and the collision tags, so the single-instance rule under **Seam** spans them.

## Provenance

VRLabs **Custom-Object-Sync** (MIT, © VRLabs) is the studied ancestor. Two of its idioms are re-derived here: the successive-approximation threshold walk that turns an analog reading into bits, and the setter tree that drives a constraint's `PositionOffset` from decoded values. Its receive side is rejected wholesale — a multi-frame decode walk is exactly what a culling pause interrupts, so every decode here is a blend tree holding no state between frames — and so is its physics world-pin and its six rotation physbones. The transport is `vrc-patterns/word-channel`, whose protocol descends from VRCFury's Parameter Compressor. Nothing is ported from either; both are credited as ancestors.

## Interface

**The consumer surface is two roles, and each is one node**: `Sync_Target` is yours to drive, `Sync` is the entry's to drive and yours to use — Custom-Object-Sync's `SyncPosition Target` / `SyncPosition` pair under the same names. Mount your prop under `Sync`, or list `Sync` as a source in a multiplexer of your own; for a carried prop add your constraint sources to `Sync_Target`'s shipped (empty) constraint. Nothing else is an install step. **The prefab root is world-pinned, so everything under it — `Sync` included — holds world scale 1 while the avatar scales**: a prop mounted there keeps its authored size at any eye height, which is what makes one dropped prop the same size for everyone whatever their wearer's scale. Want it to scale with the wearer instead? Mount it outside the pin and list `Sync` as a constraint source, which takes the pose and leaves scale yours.

The split is a two-writer rule, and it is what every composed behavior hangs off: the entry never binds `Sync_Target`, and you never bind anything under `Sync` — **binding**, not reading, so listing `Sync` as a source in a constraint of your own costs the rule nothing (§Composing against Sync). Carry, stow, world-drop, or a RemyDoll-grade authority multiplexer are all constraints and clips you compose against `Sync_Target`; the entry measures it and reconstructs, continuously, with no modes. **`Sync` is correct on both clients, which is the point of the split** — the wearer's copy rides `Sync_Target` with no decode in the path, a remote's rides the reconstruction once it is valid, and the module owns that choice so no consumer has to make it. While the prop is carried with Enable on, remotes track the reconstruction, ~1.3 s behind the true hand; drop is where this entry converges exactly, carry is where a composed remote-side swap could someday do better. No per-object sync bit, because there is no runtime object index — multi-object is a list in `generate.py`'s CONFIG, resolved at generation time into that many objects' worth of words.

- **Drop, as shipped**: the `Drop` toggle (a VRCFury `Toggle` on `Sync_Target`, its own synced bool — one bit on top of the entry's 29, deleted with the component if you never drop) animates `Sync_Target`'s constraint `FreezeToWorld`. On a sourced constraint every 0→1 edge re-captures — pin where it stands, release back to the source (`../../docs/runtime.md` §Constraints owns the measurement) — so with a hand source wired, Drop-on freezes the prop in world for the wearer instantly and the wire walks every other client to the same millimetre. **Wire a source first**: source-less, `FreezeToWorld` captures once, permanently, and nothing animatable resets it. Keep Enable on while dropping — the freeze is per-client, so only the reconstruction, not the frozen input, is the same place for everyone.

- **Params in**: `ObjectSync/Enable` (bool, synced, **unsaved**, default off) — the master gate, on `globalParams`, so an outside driver or OSC can reach it under that bare name. Nothing else: the module measures a transform, not a parameter. `Rig/Prop/Coarse/Sender`, `Rig/Prop/Fine/Sender` and `Rig/Prop/Rot/Holder` name `Sync_Target` directly — **all three constraints, carrying four contact senders** (the rotation holder has two: `MarkA`, `MarkB`), **and no assertion can hold that for you** (they live in the hand-maintained prefab, out of `--check`'s reach), so a sender left on some other transform is the one silent way to make the stages measure different objects. To measure something deeper than the input — a grab bone inside your prop — source `Sync_Target` from it rather than re-pointing a sender.
- **Menu**: one bare VRCFury `Toggle` (`CONVENTIONS.md` §The README) — `Object Sync` on `ObjectSync/Enable` from the controller's menu block — plus the composed `Drop` toggle on `Sync_Target` (VRCFury-prefixed param, deletable composition rather than module surface). The `menu:` block compiles to a committed `built/ObjectSync_Fx_Menu.asset`; the prefab's `FullController` carries `menus: []` and installs neither it nor a `Toggle` component, so the menu front is the consumer's to place. The module is single-instance per avatar regardless, for the collision-tag reason under **Seam**.
- **Params out** (every client): `ObjectSync/Ch/Acquired` (bool, **not synced**, on `globalParams`) — the transport's own correctness output, *this client's receiver has applied a complete word table since the last animator load or distance-cull pause*. The entry declares no validity param beside it. It is what a consumer hides or blends their own stand-in on; the module shows nothing of its own and hides nothing of yours. It reads **false on the wearer** (which runs no receiver) and stays **true on a remote with `Enable` off** (which never gated the wire), so the predicate a consumer actually wants is `IsLocal OR (ObjectSync/Enable AND ObjectSync/Ch/Acquired)` — drop either added term and a remote parked on `Sync_Target` reads as trustworthy. Never gate on `ObjectSync/Ch/Cycle`, word-channel's liveness counter: it answers a different question, its thresholds are apply-discipline-dependent, and being off `globalParams` it is instance-prefixed anyway (`../word-channel` §Interface owns both propositions and what each one is *not*). Also out: `Prop/PX/{C,F}` + `Prop/PX/{C0..C3,F0..F3}` and the same per axis, `Prop/R{A,B}/{X,Y,Z}` + four bools each — the word table, driven by the receiver on remotes and by the encode layers on the wearer. Everything else is `scratch:`.
- **Wire** (word-channel's synced params, all unsaved): 3 index bools + 2 8-bit int slots + 8 bool slots = **27 bits**, 6 batches, ~0.70 s full refresh at 60 fps. Plus `ObjectSync/Enable`, the entry's own synced bit, for **28 synced bits total** — the wire is what the transport costs, the total is what the avatar pays. Eight bool slots, not nine: at 12+12 bits a position group's bool tail is exactly 4+4, so a ninth slot would ride every batch idle — one synced bit for nothing. The counter spans one loop, not two: `indexLoops` divides a pause-alias probability that `atomic: batch` does not have, so a second loop would cost an index bit and 18 `Sync` states for nothing.
- **Seam**: VRCFury `FullController` on the prefab root, `basis: mount-root` ↔ the FullController default `rootBindingsApplyToAvatar: 0` — every clip binding paths through the module's own rig, so the internal hierarchy names in **Rig** below are load-bearing. `globalParams` is exactly `ObjectSync/Enable` and `ObjectSync/Ch/Acquired` — the first because the module's own `Toggle` drives it by name, the second because a consumer must be able to bind it by name and a param VRCFury has prefixed is unreachable to them; every other param takes an instance prefix, `ObjectSync/Ch/Cycle` included. That makes the *parameters* instance-safe and nothing else — the collision tags — four on the root build, three per object on `y`/`y_double` — are fixed strings VRCFury's prefixing does not reach, and two copies park their contact clusters at the same point, so a second instance needs a regeneration with its own tags, not a second drop of the prefab. **Extend this list by scoping, not by enumerating**: a consumer needing more of the module's namespace writes `ObjectSync/*` plus `!` exclusions rather than adding names one at a time, because an enumeration silently goes stale when this entry renames a param — the stale entry is dropped without a word while the new name takes an instance prefix (`../../docs/gimmicks.md` §Packaging and interface owns the grammar). The two names above are the published interface and stay enumerated *here*; scoping is for the consumer's own list.

**Retired:** `ObjectSync/Sync_Valid`, replaced by `ObjectSync/Ch/Acquired`. It is not a rename — the proposition inverted. `Sync_Valid` read true on the wearer where `Acquired` reads false forever, so a consumer porting across needs `IsLocal OR (ObjectSync/Enable AND ObjectSync/Ch/Acquired)`, all three terms, not a substituted name.
- **Dependencies**: **compose `anti-cull` alongside** — the decode runs only while a remote client evaluates the wearer's animator, and a view-culled wearer's prop freezes where it was last decoded. Distance-hide is not defeatable and is a declared limit, not a defect.
- **Required assets**: `assets/World.prefab` — the never-instantiated prefab the root's pin sources, which is what makes the frame the same world origin on every client. A bare origin node; do not instantiate or delete it. Beside it `assets/PinEnable.anim` — the clip the root's `ApplyDuringUpload` plays to re-enable both pin constraints at build. Hand-maintained and ungated, so its content is specified here: **two** float curves, both `attribute: m_Enabled` at `path: ""` (an `ApplyDuringUpload` clip resolves against its own GameObject, which is the prefab root) with value `1` — one targeting the root's `VRCParentConstraint`, one its `VRCScaleConstraint`. Nothing opens `assets/`, so a curve dropped or retargeted leaves every check green and surfaces only as a mislinked hand on someone else's avatar: a one-curve clip is the defect this shipped one exists to prevent.

## Composing against Sync

The shape both known consumers converged on independently — the operator's own doll rig and this entry's demo avatar — and the one to reach for whenever the prop has more than one authority:

    World.prefab pin (your rig root, VRCParentConstraint, Locked)
      └─ mux node          VRCPosition + VRCRotation, N sources, weights animated
         └─ damper node    VRCPosition + VRCRotation, sources (mux, self), per channel
            └─ content

`Sync` is one source in that mux, beside your hand anchors and whatever else places the prop — not the prop's parent. Nine sources is a real number, not a hypothetical one. Weight it in on the three-term predicate under **Params out** and out again when the pose is not yours to trust. That predicate is deliberately **stricter than `Follow`'s own latch**, which holds the reconstruction through a cull resume until the table re-certifies — mirror `Follow` instead only if you want your stand-in to hold through that window too. Pin your rig root at **zero** source offset, like `Rig`'s own pin: the shipping client scales a source's `ParentPositionOffset` by the avatar's scale factor (the park row under **Rig** owns the mechanism), so any world offset you need belongs on a child transform under the pin, never on the pin itself — and keep that child under the scale pin, which is what holds its local position at true metres. **The entry ships that pin, on its own prefab root** — `VRCParentConstraint` + `VRCScaleConstraint` → `World.prefab` at zero offset, both `m_Enabled 0`, re-enabled at build by an `ApplyDuringUpload` playing `assets/PinEnable.anim` — so a composition parents its content under the entry rather than hand-authoring a pin above it. **Do not enable those constraints to make the editor view look pinned.** They ship disabled because a consumer may put an `ArmatureLink`, a `BoneProxy`, or any seam that captures a world pose beneath them, and the entry cannot know: an editor-solved pin holds that seam at the world origin whatever the avatar's position and scale, and the build bakes the origin-parked pose instead of the one authored on the body (`../../docs/gimmicks.md` §Constraint patterns owns the swap and the trap it replaces). The measured cost of getting this wrong is 0.715460 m of anchor-to-bone mislink at avatar scale 1.7, against 0.000001 m or less once swapped.

**Damping belongs on your damper node, never inside this entry.** A module-side damper could only smooth its own source, leaving every other mode in your mux unsmoothed, and two dampers in series on the sync path is worse than either alone. It would also cost a channel: position wants lag where rotation usually wants none, and that is two weights, not one. How much smoothing is worth buying depends on the prop, which is the other reason the choice is yours: under `atomic: batch` each batch applies as it lands, so a resting prop's reconstruction moves only by quantization — 0.1–0.75 mm end to end, the constants table's figure — and damping it is cosmetic, while a moving one steps by whatever it travelled over a full ~0.70 s refresh, one axis at a time as that axis's batch arrives. Custom-Object-Sync damps because its reconstruction jitters continuously; this one is quiet at rest and coarse in motion, and a damper pays for either with τ × speed of further lag on the path already worst-off for latency. `../spring-damping` owns the law and the time constant.

**A damper's parent must be inertially static; its target may move freely.** That is why the tier above it is pinned to `World.prefab` — the same pin `Rig` carries here, and for the same reason. A damper whose parent moves is dragged by its parent's motion, measured at ~21× the per-frame parent step at a 1:0.05 weight.

With more than one object, the surface pair gains the object name rather than staying bare — a `Sync{Obj}` / `Sync{Obj}_Target` pair per object, one input being one consumer-driven frame and one output following one reconstruction (Custom-Object-Sync ships the same suffixed-sibling shape as `SyncPositionA Target`/`SyncPositionA`) — each object gets its own collision-tag set (below), and the `m_IsActive` bindings on the measure subtrees pass from the enable's clips to the `Slice` layer's, which owns them alone.

Multi-object measurement is ONE shared walk set, not a walk set per object — the slice already serializes measurement, so the walks run once per slice against shared `Sh` staging and a per-object `Commit_<o>` routes the words to whichever object's slice is live, which is what keeps layers and walk states flat in N. Two consequences bind the hand-built rig. **Every object's receivers name the SHARED sense params** (`ObjectSync/Sense/Sh/…` — the committed `y_double` prefab is the template): receivers multiplex onto one param set with at most one live writer, because the slice's gate clip deactivates the outgoing rig and activates the incoming one in a single evaluation — no co-active frame exists, and the handoff rests on three properties this entry already measures elsewhere (a deactivated receiver stops writing, the Enter clear sticks because the deactivation preceded it, liveness gates the re-acquired reading). Client-measured corroboration: with two receivers deliberately co-active on one param, the last-enabled receiver's write wins deterministically — but the emulator arbitrates by fixed receiver order instead, so any rig that actually DEPENDS on enable-order arbitration is client-tier-only (`../../docs/verify.md`), and this one deliberately does not. More than two receivers per param is unmeasured in-client; the committed surface stays at two. **Collision tags stay per-object** (the table below): tags fence senders, which are constrained to different targets, and the shared sense params do not change that. Slice weighting is generation-time: an object with `slices: k` in CONFIG takes k interleaved turns in the ring (never two consecutive — an adjacent repeat's Enter would tear down its own in-flight walk), which is what buys a hot object its refresh rate back at N objects.

A `y`-mode rig is this one with `MarkB`, `RecvAY`, the three `RecvB*`, `ProxyB` and `UpAim` deleted, and `Recon` re-parented to `Recon/` carrying `WorldUpType: Vector`, `WorldUpVector (0,1,0)` instead of the object-rotation up. Nothing else moves.

## How it works

**Position, per axis, in two stages.** A `VRCPositionConstraint` squeezes the prop toward the rig anchor — anchor weight `1 − g`, prop weight `g = coarseHalfSpan/range` — so the whole ±4096 m range lands inside ±2.75 m of a 6 m face receiver. An `IsLocal` successive-approximation walk (one state pair per bit, accepted above, rejected below) turns that reading into 12 bits naming a 2 m **cell**. The walk's accumulated cell index places a second anchor at that cell's centre, and a sender constrained to the prop is read at 1:1 by face receivers riding that anchor, which a second walk turns into 12 more bits. Anchor, receiver and sender share one hierarchy, so the float32 displacement the avatar's own distance from the world origin introduces appears identically on both sides of the subtraction and cancels bit-exactly — measured identical to the last bit with the avatar parked at 0 m and at 5 km.

**Why 12+12 and not 12+11.** The coarse stage does *not* cancel that displacement: at range its world error runs to 0.58 m, over a quarter-cell with margin on top, so the cell it picks can be one boundary out. The fine field is therefore **redundant** — it spans the cell plus twice the guarded coarse error (3.2 m), not the cell (2 m) — so an off-by-one cell is still reconstructed exactly, at the cost of one bit per axis and no correction pass anywhere. That 3.2 m field sits inside the 6 m face with 1.4 m spare at each end, which is what keeps the readout off the two ways a face receiver lies: it saturates at 1.0 for about 20 mm past the face plane, and past that it reads exactly 0 — the same value as "nothing overlaps".

**Rotation without trig or physbones.** A rotation-only holder carries two markers on orthogonal 1 m arms; three face receivers per marker give six components, sent raw. Every client rebuilds the orientation with a `VRCAimConstraint` pair: `UpAim` aims +Y at proxy B, and `Recon` — **its child**, so the solver is forced to resolve `UpAim` first in the same frame — aims +Z at proxy A with `WorldUpType` **ObjectRotationUp** against `UpAim`. `ObjectUp` looks like the right token and silently degenerates to world up; it is never correct here. The `y` preset is a strict subset of the same rig — marker A's X and Z components on the wire, one `Recon` aim constraint with `WorldUpType` **Vector** `(0,1,0)`, no second marker and no `UpAim` — and it sends components rather than the heading itself because a parameter driver reads 0 from an AAP, so no walk can quantize a number a blend tree computed. Its two components are not two values, though: they are one heading, and BOTH halves of that need a single frame — the sampling and the publication. One **serial pair layer** owns it: its `Start` driver copies both residuals in one frame, the A/X ladder walks its frozen residual, its final pair steps straight into the A/Z ladder's first decision (no state between `Start` and the commit reads a sense param), and one commit publishes all 24 bits. Serializing costs nothing in cycle time — the pair runs 27 frames against the position walk's 33, so the slower ladder still sets the slice — and sampling both components in one driver is what makes the committed pair an angle the marker actually held at some instant, whatever the yaw rate. Full mode's six components genuinely are independent readings from two markers, so a torn set of them is a stale orientation rather than one no marker held, and in the single-object build they keep a walk and a commit each; a multi-object build routes A/X + A/Z through the same shared pair layer (one sample frame and one commit cost an independent pair nothing) and the four full-only components through shared per-component walks.

**The wire, and why nothing tears.** Each axis's coarse byte, fine byte and eight bools share one `group:`, so word-channel pins them into one batch and `atomic: batch` applies them together: an adjacent-cell coarse always lands with its matched fine, which reconstructs the same position, so cell-boundary flicker needs no hysteresis anywhere. Each rotation component's byte and four bools share a cross-kind group the same way, and `y` mode's two heading components share one group as well. The walks are multi-frame and that is safe — they run only on the wearer's own client, which cannot cull itself — but the handoff to the wire must not be, because word-channel's sender copies the word params on its own clock and would happily latch a half-written axis. So the walks fill scratch staging and one `Commit` state driver-copies a whole axis, all ten words, in a single frame. The rotation walks are the same rule applied to whatever counts as one value: a commit each in full mode, and in `y` one serial pair layer sampling both heading limbs in one frame and committing them in one.

**Two anchors, not one.** The measurement anchor rides the walk's running cell index — a staged value, mid-cycle, local. The display anchor rides the committed word and is side-agnostic: the wearer decodes its own prop from the same words a remote does. They cannot be one node, because sharing would mean committing the coarse word before the fine walk has run, which is exactly the torn axis the commit exists to prevent.

**The decode reads one-frame-old copies of every word limb — bytes included — and the bytes are the load-bearing half of that sentence.** A blend tree cannot weigh a bool, so a `Floatify` driver mirrors the word bools into float scratch one frame late; the byte words are already tree-readable, and reading them raw is a measured defect rather than a saved copy: byte on the direct path, bool tail on the copy path, and the assembled `D/…` pair mixes new and stale for one frame on every coarse-word change. Measured on both the emulator and the shipping client (at the 13-bit geometry; the mechanism is bit-width-independent and the current 12+12 tail caps the excursion at ±15 cells): a one-frame display excursion of exactly one cell (2.0 m) per cell crossing, and ±62 m where the crossing landed on a coarse byte boundary — bool tail wrapping to 0 against byte +1, read mixed — which in game reads as the prop vanishing for a frame and which a consumer's damper integrates into a visible lurch. Routing the bytes through the same `Floatify` copy lands an axis's whole word at the decode together, whatever a venue's driver-to-tree propagation timing, wearer and remote alike, for one frame of decode latency and no new state; nothing asserts this, so the fast path can creep back — in `Decode` or any later layer — and review is the only guard. This is the decode-side complement of the wire's grouping: `group:` keeps coarse and fine together across the network, the shared copy keeps them together across the last frame into the tree. The decode and the display ride ONE single-state Direct layer, not two: an AAP read is one frame behind its write for same-layer and cross-layer trees alike (`../../docs/runtime.md` §Animator evaluation), so the display children read the `D/` values at the same latency a separate layer gave them, all of one age — merging costs nothing and saves a layer.

**Who drives the prop.** `Sync`'s constraint is the entry's whole reach into the consumer's hierarchy, and the `Follow` layer moves weight between its two sources. **It is a latch, not a predicate held both ways**: an AnyState rung with `canTransitionToSelf: false` engages the reconstruction on `!IsLocal AND ObjectSync/Enable AND ObjectSync/Ch/Acquired` — the `Acquired` term read through its `Floatify` copy, because the receiver certifies it in the same driver frame that writes the final batch's words, one frame ahead of their copies, and engaging on the raw param would render the last group stale on a head-landing cold join — and the only exit tests `Enable` alone — so once engaged it holds through whatever `Acquired` does after, and a receiver falling to `Lost` mid-session does not drop the prop back to its target. Add a rung here without deciding what it does to that, and you un-latch it. Enable-off, a pre-gate remote and a culled decode still collapse to one case on the way in — `Sync` rides `Sync_Target` — so the module hides nothing of yours and shows nothing of its own. A layer rather than a rung of the enable's blend tree, because `IsLocal` is a bool built-in and a tree reads 0 from it forever. The `Acquired` term is the late-joiner gate: a fresh clone's word table is all zeros, zero is cell 0, and cell 0 is the corner of the range, so engaging before a whole table has arrived would show the corner — and taking the transport's own certification means no threshold here shifts if the apply discipline changes. Three states over two clips, because the wearer and a pre-gate remote hold the same pose and opposite validity, and one state cannot say both; none of the three drives a parameter, since the proposition a consumer needs is already `Acquired`. The wearer's copy never rides the decode: it moves under whatever the consumer's own system gives it, with no decode in the path and no constraint of ours between the carry constraint and the prop.

**The enable, and what it does not gate.** `ObjectSync/Enable` is one synced bit, so wearer and remotes park together. Off, a 1D tree on it deactivates the three measure subtrees; each measuring layer takes an AnyState rung into a `Parked` state whose driver clears that layer's staging, residual, cell index and sense params — in that order, because a deactivated sensing component does not fall to zero, it *freezes* at its last live reading, and only a clear written after the deactivation sticks. What Enable does **not** gate is the wire: word-channel's 27 bits are allocated whether or not the prop is out, so gating it would save nothing and would cost the re-enable a full re-lock. The word table is left holding the last committed pose for the same reason — re-enabling shows the prop where it was, not at the origin. One consequence, intended: because the receiver keeps decoding through the toggle, `ObjectSync/Ch/Acquired` stays true across an Enable-off, and flipping Enable back on **engages on that frame** rather than waiting out a cycle.

**Coming back up is where a clear turns into a lie.** A cleared sense param reads 0, and 0 quantizes to cell 0 — the far corner of the range — so a walk that samples before its reactivated receivers have re-acquired publishes a confident wrong answer rather than nothing. Walks therefore gate on **receiver liveness**, not on a timer: a 0 reading is never legal in-volume, which is the edge guard's second job, and every walk-entry transition additionally requires the very params that walk is about to sample to read above a threshold derived from that same guard. Re-acquisition measured 7 frames in the emulator, is unbounded in principle, and the gate does not care. The road to any `Commit` likewise runs through every bit of the walk. Both are transition structure rather than a timing argument, and neither is asserted. The multi-object `Slice` layer is the same discipline at slice granularity — deactivate every other object's rig, clear, wait for this one's receivers to come live, then unblock its walks — with a bounded skip so a rig that never wakes yields its slice instead of starving the others, and a second AnyState rung making a walk that loses the rig mid-flight abandon rather than commit limbs measured against somebody else's senders. The hand-off out of a slice is gated the same way, on the walks' own `Slice/Done` commit stamps rather than a dwell: the walks step one state per frame while an `exitTime` is wall-clock seconds, so a fixed Run window is a frame budget divided by an assumed frame rate, and at any rate where the budget stops fitting, the abandon rung beheads the slowest walk on every cycle while shorter ones still commit — position words frozen at zero under a live, replicating heading is that defect's exact fingerprint (every decoded prop then parks at the range corner, kilometres out). The wall-clock escape survives only as the yield bound on a slice that cannot finish — a rig that wakes but never converges, the fine stage escaping under fast motion — sized at CONFIG's `sliceFloorFps`, where it costs nothing in normal operation.

**A gate is only safe where waiting can end.** A liveness wait survives exactly when its condition can be restored without the machine advancing past the wait, and one wait fails that test: the fine receiver rides the measurement anchor, and only a fresh coarse commit moves it. Teleport the prop out of its current cell while the walk is past the coarse stage and the fine sender leaves its box for good, so that wait blocks on a stage it can no longer reach — measured in a venue as 2 of 5 instantaneous teleports stalling the position stage indefinitely while rotation, whose markers cannot leave their boxes, kept tracking. The fine wait therefore carries the machine's one escape: after `fineEscapeFrames` of dead reading it abandons to `Idle`, which restages the cell, snaps the anchor and restores overlap. Every other wait is on a source that restores itself — the coarse receiver's box spans the whole working volume, and the rotation markers ride rigid arms — and `generate.py`'s liveness audit records which is which, unasserted — so a new gate added without an entry saying why waiting there ends passes every check.

The failure mode that buys is the one this entry is built around: a rig that never wakes leaves its walk waiting and the wire holds the last committed pose. Nothing publishes a position it did not measure, and nothing waits on a reading that will never come.

**Costs.** **370 states and 14 layers** for the root build (248/9 and 269/10 for `y/` and `y_double/` — read them off the generator's own compile line, which prints both, rather than off the previous figure plus a delta); 33 frames (~0.55 s) per local measure cycle, plus however long the receivers take to come live after an unpark, ~0.70 s per wire refresh, ~1.3 s worst case end to end. A multi-object build costs a slice per ring slot instead, ~0.8 s per slice — and the shared walk set is why N objects cost walk states once, not N times (the generator's compile line is the meter: a six-object document lands near 14 layers, not 43). Twelve local-only receivers per full-rotation object, eight per y object, zero physbones; the `Floatify` driver copies every word limb plus `Acquired` (60+1 params on the root build, 40 per y object thereafter) every frame on every client — one driver however many objects, and the term that scales worst with N. The design also has a speed ceiling: sustained authority motion faster than roughly the fine field over one measure-plus-wire interval (≈ 5–6 m/s at 60 fps for the committed single-object geometry) walks the fine sender out of its box every cycle, so the escape restages continuously and the display holds the last good commit rather than tracking — measured at 12 m/s as a clean hold, 1.5 m/s as normal ~1.3 s-lag tracking. At N objects that interval stretches by the ring, and slice weighting is the knob that buys a hot object back: its ceiling is the fine field over ITS OWN slice period, so derive it from the object's share of the ring, never from the single-object figure. A droppable prop never reaches it; a projectile consumer is out of scope by construction, not by tuning. `generate.py --check` holds regeneration byte-identical for all three committed documents and asserts collision-tag uniqueness across objects and stages. Packing, commit reachability, the liveness gate on every walk entry, the slice sequencing, the reconstruction shapes, and the rule that no driver anywhere reads or writes an AAP param are all unasserted — that last is the shape of the defect that cost y-mode its first design, and only review catches it.

## Verifying the install

Cheapest observable: **move `Sync_Target` with the wearer standing away from the world origin and facing away from +Z**. On the wearer, `Sync` must track it frame-for-frame; any lag there means the local branch is riding something it must not. On a remote clone, `Sync` reaches the same world pose inside about a second — millimetres of position, hundredths of a degree of rotation, the same value on both sides because both decode the same words — and `ObjectSync/Ch/Acquired` must be true on that clone. Its two other readings look like faults and are not: **false on the wearer**, and **true on a clone with Enable off** — Enable changes which source `Sync` rides, never whether the table is real. The off-origin, off-axis stance is the part that is easy to skip and the part that catches the whole class: a rig frame that has quietly stayed avatar-relative is indistinguishable from a correct one at the origin, so read `Rig` while you are there and require exactly `(0, 0, 0)` with identity rotation on both clients, with `Rig/Prop` at exactly `(73, 932, 233)` and the pin's source offset zero — and lossy scale exactly `(1, 1, 1)` with the avatar scaled away from upload height (av3emu: `EnableAvatarScaling` + `AvatarHeight` on the local runtime), which is the check that catches a lost scale pin: unpinned, the fine receivers read exactly 0 past the Rig table's `|scale−1| > 0.0013` bound while coarse and rotation stay green, the same verdict a world eye-height clamp produces in game. Local and clone disagreeing by more than quantization is the decode reading a different word table, not the wire being slow; a clone's `Sync` frozen while `VF##_ObjectSync/Ch/Cycle` climbs is the rig rather than the wire (`../word-channel`'s own §Verifying owns that reading, and why the counter carries a per-build instance prefix). On a cold join `ObjectSync/Ch/Acquired` is false and the prop rides `Sync_Target` for **one to two loops (~0.7–1.4 s)** before the reconstruction takes over already at its synced pose — a late joiner never sees the range corner at all. **The spread is the normal reading, not a fault**: under `atomic: batch` the receiver re-locks at any counter value, and only a join landing on a batch head certifies at that loop's tail. For the drop path: with a hand source on `Sync_Target` and Enable on, Drop-on must freeze the wearer's prop on that frame and walk a clone to the same world pose inside the usual ~1.3 s; Drop-off must snap the wearer's prop back to the hand on that frame — any wearer-side lag on either edge means something other than `FreezeToWorld` is in the local path.

Two more reads on a multi-object build, both cheap in the same session. **The shared sense params across a slice boundary**: exactly one nonzero writer at any moment, exactly 0 through an Enter's clear gap, and no reading surviving from the outgoing object into the incoming object's walk entry — the Enter clear plus the liveness gates are what stand between a graceful wait and a cross-object publish, so a stale value here is the highest-severity fault this rework can have. **A y object under continuous yaw**: every committed heading pair must reconstruct an angle the marker actually held at some instant — a commit mixing two sample times reads as a heading sweeping THROUGH angles the prop never faced, and the pair layer's single-frame sampling exists precisely so that cannot happen.

What the emulator structurally cannot show for this entry: everything `../word-channel` declares — its wire is this entry's wire — plus four that belong to the measure rig. **Contacts are never simulated against a remote clone**, so the twelve receivers are only ever exercised on the wearer's own client, and nothing here can reach a fault that needs another player's dynamics to appear — which is also why the park is an argument rather than a measurement: `(73, 932, 233)` is empty in a test scene by construction, where a real world may put geometry or another player's props through it. And **contact re-registration latency is the emulator's, not the client's**: a reactivated receiver takes 7 frames here, the shipping client is unmeasured, and the design gates on the reading rather than on that number precisely so the difference cannot matter. **Contact readout temporal noise is the client's, not the emulator's** — present at rest, amplified by wearer motion. The emulator's sense values are bit-constant frozen-and-stationary at every range (measured 0–8 km); the client's jitter continuously even at rest — about a tenth of a cell of span at 1000 m over a ~30 s window, a margin, not a guarantee: no word change was observed, but a pose parked close enough to a cell boundary still can commit. It is *wearer motion* that swings the readout of a world-frozen target to a full cell of span at 1000 m, dithering the committed coarse word at roughly one event per second (measured in-client under desktop movement). Distinguish that from the constants table's 0.39 mm coarse error, which is a static position-dependent bias both venues share. A dithered pair still reconstructs the true position — the redundant fine field absorbs an off-by-one cell by design — so at the measured range the dither costs accuracy nothing and matters only as extra coarse-word events, each of which the decode must (and, since the shared `Floatify` copy, does) apply coherently. That free-ness is bounded, not structural: the motion swing is ±0.52 m of world equivalent at 1000 m (the squeeze scales it with `range/coarseHalfSpan`, so the measured 13-bit figure halves at this geometry) against the fine field's ±0.60 m coarse guard — the same ~13% headroom — and the guard was sized for the static at-range bias this term adds to, so past 1000 m, where the swing is unmeasured and scales with distance, the off-by-one absorption is not known to hold. A fourth gap is the one the zero-offset pin closes: **the emulator SDK never scales a constraint source's offset by avatar scale, so a park that crept back onto any source offset would pass every emulator check and still misplace the prop cross-client.** The emulator-expressible shadow is the injected-scaling fixture: in play mode, apply the client's rule by hand — multiply every source offset on the remote clone's root pin constraints by a forced-scale factor (×1.35, say) — and require local/clone `Sync` agreement unchanged, which holds exactly when every offset is zero; injecting a park-sized offset first and watching agreement break by that vector is the teeth check. `generate.py --check` holds part of the static half — no nonzero source offset in any committed prefab, while the document's animated source-space offsets are unasserted — and only an in-client two-scale read (`../../docs/runtime.md` §Constraints) sees the real client behavior.

# object-sync — absolute world position + rotation for a droppable prop (Module)

A prop that can be set down anywhere in the world and is in the same place for everyone, including a player who joins after it was dropped: a two-stage contact measure quantizes its world transform on the wearer's client and `word-channel` replicates the bits, with no physbone, no Rigidbody, and no synced position of its own. The packaged novelty is the redundant fine stage — a second, bias-cancelling readout wide enough to absorb the coarse stage's error — which puts sub-millimetre placement anywhere in a ±4096 m world inside **28 synced bits** — a 27-bit transport wire plus the one enable bit — refreshed end to end in ~0.7 s.

Three built configurations ship, each with its own regenerated document, compiled controller and prefab, so a download is usable without this workspace: the entry root (one object, full rotation), `y/` (one object, heading only) and `y_double/` (two objects, heading only, time-multiplexed onto one measure rig and ONE shared walk set). One build per FullController component, whichever variant; a second build on the same avatar is a regeneration with its own `rigSeed` — the parameters are sealed identical by design, and only the collision tags and the park may, and must, differ (**Seam**).

## Provenance

VRLabs **Custom-Object-Sync** (MIT, © VRLabs) is the studied ancestor. Two of its idioms are re-derived here: the successive-approximation threshold walk that turns an analog reading into bits, and the setter tree that drives a constraint's `PositionOffset` from decoded values. Its receive side is rejected wholesale — a multi-frame decode walk is exactly what a culling pause interrupts, so every decode here is a blend tree holding no state between frames — and so is its physics world-pin and its six rotation physbones. The transport is `vrc-patterns/word-channel`, whose protocol descends from VRCFury's Parameter Compressor. Nothing is ported from either; both are credited as ancestors.

## Ground truth

**The consumer surface is two nodes, plus one read** — `Rig/<obj>/Display` is the reconstruction before `Follow` arbitrates, to source for the decoded pose unarbitrated. `Sync_Target` is yours to drive, `Sync` is the entry's to drive and yours to use — Custom-Object-Sync's `SyncPosition Target` / `SyncPosition` pair under the same names. Mount your prop under `Sync`, or list `Sync` as a source in a multiplexer of your own; for a carried prop add your constraint sources to `Sync_Target`'s shipped (empty) constraint. **The prefab root is world-pinned, so everything under it — `Sync` included — holds world scale 1 while the avatar scales**: a prop mounted there keeps its authored size at any eye height, which is what makes one dropped prop the same size for everyone. To scale with the wearer instead, mount outside the pin and list `Sync` as a constraint source, which takes the pose and leaves scale yours.

The split is a **two-writer rule**, and every composed behavior hangs off it: the entry never binds `Sync_Target`, you never bind anything under `Sync` — **binding**, not reading, so listing `Sync` as a source of your own costs the rule nothing (§Composing against Sync). Carry, stow, world-drop, or an authority multiplexer are all constraints and clips you compose against `Sync_Target`; the entry measures it and reconstructs, continuously, with no modes. **`Sync` is correct on both clients, which is the point of the split** — the wearer's copy rides `Sync_Target` with no decode in the path, a remote's rides the reconstruction once it is valid, and the module owns that choice so no consumer has to. A carried prop's remote tracks the reconstruction ~1.3 s behind the true hand; drop is where this entry converges exactly. No per-object sync bit: multi-object is a list in `generate.py`'s CONFIG resolved at generation time, not a runtime index.

- **Drop, as shipped**: the `Drop` toggle (a VRCFury `Toggle` on `Sync_Target`, its own synced bool — one bit on top of the entry's 28, deleted with the component if you never drop) animates `Sync_Target`'s constraint `FreezeToWorld`. On a *sourced* constraint every 0→1 edge re-captures — pin where it stands, release back to the source (`../../docs/runtime.md` §Constraints) — so with a hand source wired, Drop-on freezes the prop in world for the wearer instantly while the wire walks every other client to the same millimetre. **Wire a source first**: source-less, `FreezeToWorld` captures once, permanently, and nothing animatable resets it. Keep Enable on while dropping — the freeze is per-client, so only the reconstruction is the same place for everyone.

- **Params in**: `ObjectSync/Enable` (bool, synced, **unsaved**, default off) — the master gate, on `globalParams`, reachable by an outside driver or OSC under that bare name. To ship it armed, CONFIG's `enableDefault` (Rig table, Enable row). Nothing else: the module measures a transform, not a parameter. The three measure constraints (four contact senders — **Rig**) all name `Sync_Target` directly, and nothing checks it: they live in the hand-maintained prefab, out of `--check`'s reach, so a sender left on some other transform is the one silent way to make the stages measure different objects. To measure something deeper than the input — a grab bone inside your prop — source `Sync_Target` from it rather than re-pointing a sender.
- **Menu**: the `menu:` block compiles to a committed menu asset, but the prefab's `FullController` installs neither it nor a `Toggle` — **the menu front is the consumer's to place**. Dropping one prefab twice is still broken regardless — the two copies share tags and park; a second object is a regeneration (**Seam**).
- **Params out** (every client): `OS/Ready` (bool, **not synced**, sealed — a consumer reads it through the same-component merge under **Seam**) — the correctness output: *this client's receiver has applied a complete word table since the last animator load or distance-cull pause*. It reads **false on the wearer** (which runs no receiver) and stays **true on a remote with `Enable` off** (which never gated the wire), so the predicate a consumer actually wants is `IsLocal OR (ObjectSync/Enable AND OS/Ready)` — drop either added term and a remote parked on `Sync_Target` reads as trustworthy. `Ready` is the `Floatify` copy of word-channel's `OSCh/Acquired`, declared beside it: engage on `Ready`, invalidate on raw `OSCh/Acquired` where the earliest falling edge is what you want. Never gate on `OS/Ch/Cycle`, word-channel's liveness counter (`../word-channel` §Interface). Also out: the per-axis word table (`Prop/…`), driven by the receiver on remotes and the encode layers on the wearer; everything else is `scratch:`.
- **Wire** (word-channel's synced params, all unsaved): 3 index bools + 2 8-bit int slots + 8 bool slots = **27 bits**, 6 batches, ~0.70 s full refresh at 60 fps; plus `ObjectSync/Enable` for **28 synced bits total** — the wire is what the transport costs, the total is what the avatar pays.
- **Seam**: VRCFury `FullController` on the prefab root, `basis: mount-root` ↔ the FullController default `rootBindingsApplyToAvatar: 0` — every clip binding paths through the module's own rig, so the internal hierarchy names in **Rig** below are load-bearing; a consumer generating its own build can prefix every binding with CONFIG's `mountPath`, which is what lets that build merge through a component sitting ABOVE the rig (its mount GO's parent) with no reliance on VRCFury's ancestor walk-up. **The interface is sealed.** `globalParams` is exactly `ObjectSync/*` — one wildcard carrying the whole published interface, and the only name under that prefix is `ObjectSync/Enable` (the module's own `Toggle` drives it by name; OSC reaches it bare). Every other declared param takes the VRCFury instance prefix: `OS/Ready`, `OSCh/Acquired`, the internal `OS/` walks, and the per-object word roots (`Prop/…`, kept bare so the decode's float mirrors don't compose `OS/B/OS/Prop/…`). The list derives from the interface, not an enumeration, so adding an internal param can never widen what is exposed. **A consumer that must read a sealed name merges its own controller through the SAME FullController component as this build's** — one component prefixes every merged controller identically, so the shared names unify; `compositions/grab-sync` and `compositions/object-sync-demo` are the worked examples. Two costs ride that idiom: controller ORDER inside the component decides first-wins parameter defaults (`compositions/grab-sync/controller.yaml`'s header owns the trap), and splitting the controllers onto two components un-unifies every shared name with **no build error** — the second controller's copy silently becomes a distinct `VF*` param, and `ReportComposition` then reads the pair as `ambiguous` plus `built-only` rows, which is its correct verdict on two sealed builds, not a defect. Two builds on one avatar are exactly that: two components, each its own prefab from a regeneration with its own `rigSeed` — the parameters seal themselves apart automatically, and the only surfaces that must differ, the collision tags and the park, both derive from that one seed (run `generate.py --check`). `ObjectSync/Enable` is ONE bare param across every build on the avatar, and its baked default and flags merge first-wins across the components too — measured: an entry build at `enableDefault: 0` beside a consumer's default-1 declaration bakes default 0 — so a build that must spawn armed cannot rely on its own declaration once another build shares the avatar. An OSC consumer with a real need for `Ready` adds it to their own component's `globalParams`; the entry never publishes it (`../../docs/gimmicks.md` §Packaging and interface owns the exposure grammar).
- **Dependencies**: **compose `anti-cull` alongside** — the decode runs only while a remote client evaluates the wearer's animator, and a view-culled wearer's prop freezes where it was last decoded. Distance-hide is not defeatable and is a declared limit, not a defect.
- **Required assets**: `assets/World.prefab` — the never-instantiated prefab the root's pin sources, which is what makes the frame the same world origin on every client. A bare origin node; do not instantiate or delete it. Beside it `assets/PinEnable.anim` — the clip the root's `ApplyDuringUpload` plays to re-enable both pin constraints at build. Hand-maintained and ungated, so its content is specified here: **two** float curves, both `attribute: m_Enabled` at `path: ""` (an `ApplyDuringUpload` clip resolves against its own GameObject, which is the prefab root) with value `1` — one targeting the root's `VRCParentConstraint`, one its `VRCScaleConstraint`. Nothing opens `assets/`, so a curve dropped or retargeted leaves every check green and surfaces only as a mislinked hand on someone else's avatar: a one-curve clip is the defect this shipped one exists to prevent.

## Composing against Sync

The shape both known consumers converged on independently — a private doll rig and this entry's demo avatar — and the one to reach for whenever the prop has more than one authority:

    World.prefab pin (your rig root, VRCParentConstraint, Locked)
      └─ mux node          VRCPosition + VRCRotation, N sources, weights animated
         └─ damper node    VRCPosition + VRCRotation, sources (mux, self), per channel
            └─ content

`Sync` is one source in that mux, beside your hand anchors and whatever else places the prop — not the prop's parent. Nine sources is a real number, not a hypothetical one. Weight it in on the three-term predicate under **Params out** and out again when the pose is not yours to trust. Pin your rig root at **zero** source offset, like `Rig`'s own pin: the shipping client scales a source's `ParentPositionOffset` by the avatar's scale factor (the park row under **Rig** owns the mechanism), so any world offset you need belongs on a child transform under the pin, never on the pin itself — and keep that child under the scale pin, which is what holds its local position at true metres. **The entry ships that pin, on its own prefab root** — `VRCParentConstraint` + `VRCScaleConstraint` → `World.prefab` at zero offset, both `m_Enabled 0`, re-enabled at build by an `ApplyDuringUpload` playing `assets/PinEnable.anim` — so a composition parents its content under the entry rather than hand-authoring a pin above it. **Do not enable those constraints to make the editor view look pinned.** They ship disabled because a consumer may put an `ArmatureLink`, a `BoneProxy`, or any seam that captures a world pose beneath them, and the entry cannot know: an editor-solved pin holds that seam at the world origin whatever the avatar's position and scale, and the build bakes the origin-parked pose instead of the one authored on the body (`../../docs/gimmicks.md` §Constraint patterns owns the swap and the trap it replaces). The measured cost of getting this wrong is 0.715460 m of anchor-to-bone mislink at avatar scale 1.7, against 0.000001 m or less once swapped.

**Damping belongs on your damper node, never inside this entry.** A module-side damper could only smooth its own source, leaving every other mode in your mux unsmoothed, and two dampers in series on the sync path is worse than either alone. It would also cost a channel: position wants lag where rotation usually wants none, and that is two weights, not one. How much smoothing is worth buying depends on the prop, which is the other reason the choice is yours: under `atomic: batch` each batch applies as it lands, so a resting prop's reconstruction moves only by quantization — 0.1–0.75 mm end to end, the constants table's figure — and damping it is cosmetic, while a moving one steps by whatever it travelled over a full ~0.70 s refresh, one axis at a time as that axis's batch arrives. Custom-Object-Sync damps because its reconstruction jitters continuously; this one is quiet at rest and coarse in motion, and a damper pays for either with τ × speed of further lag on the path already worst-off for latency. `../spring-damping` owns the law and the time constant.

**A damper's parent must be inertially static; its target may move freely.** That is why the tier above it is pinned to `World.prefab` — the same pin `Rig` carries here, and for the same reason. A damper whose parent moves is dragged by its parent's motion, measured at ~21× the per-frame parent step at a 1:0.05 weight.

With more than one object, the surface pair gains the object name — a `Sync{Obj}` / `Sync{Obj}_Target` pair per object (Custom-Object-Sync's suffixed-sibling shape, `SyncPositionA Target`/`SyncPositionA`) — each object gets its own collision-tag set (below), and the measure subtrees' `m_IsActive` bindings pass from the enable's clips to the `Slice` layer's, which owns them alone.

Multi-object measurement is ONE shared walk set, not one per object — the slice already serializes measurement, so the walks run once per slice against shared `Sh` staging and a per-object `Commit_<o>` routes the words to the live object's slice, keeping layers and walk states flat in N. Two consequences bind the hand-built rig. **Every object's receivers name the SHARED sense params** (`OS/Sense/Sh/…`; the committed `y_double` prefab is the template): they multiplex onto one param set with at most one live writer, because the slice's gate clip deactivates the outgoing rig and activates the incoming one in a single evaluation — no co-active frame exists, and the handoff rests on three properties measured elsewhere in this entry. Client-measured: with two receivers deliberately co-active on one param, the last-enabled receiver's write wins deterministically — but the emulator arbitrates by fixed receiver order, so any rig that DEPENDS on enable-order arbitration is client-tier-only (`../../docs/verify.md`), and this one deliberately does not (more than two receivers per param is unmeasured in-client; the committed surface stays at two). **Collision tags stay per-object** (table below): tags fence senders constrained to different targets, and the shared sense params don't change that. Slice weighting is generation-time — an object with `slices: k` in CONFIG takes k interleaved turns in the ring (never two consecutive, whose Enter would tear down its own in-flight walk), which buys a hot object its refresh rate back at N objects.

A `y`-mode rig is this one with `MarkB`, `RecvAY`, the three `RecvB*`, `ProxyB` and `UpAim` deleted, and `Recon` re-parented to `Recon/` carrying `WorldUpType: Vector`, `WorldUpVector (0,1,0)` instead of the object-rotation up. Nothing else moves.

## How it works

**Position, per axis, in two stages** (mechanism in `generate.py`'s docstring). A coarse `VRCPositionConstraint` squeezes the prop toward the rig anchor — prop weight `g = coarseHalfSpan/range` = `0.00067138671875`, anchor weight `1 − g` = `0.99932861328125` — so the whole ±4096 m range lands inside ±2.75 m of a 6 m face receiver, and an `IsLocal` successive-approximation walk turns that reading into a 12-bit **cell**. The cell index places a second anchor at the cell centre; a sender constrained to the prop is read there at 1:1 and a second walk adds 12 more bits. Anchor, receiver and sender share one hierarchy, so the float32 displacement the avatar's own distance from the world origin introduces cancels bit-exactly — measured identical to the last bit with the avatar parked at 0 m and at 5 km.

**Why 12+12 and not 12+11.** The coarse stage does *not* cancel that displacement — at range its world error runs to 0.58 m, over a quarter-cell — so the cell it picks can be one boundary out. The fine field is therefore **redundant**: it spans the cell plus twice the guarded coarse error (3.2 m), not the cell (2 m), so an off-by-one cell still reconstructs exactly, at the cost of one bit per axis and no correction pass (`generate.py`'s docstring derives the 12+12). That 3.2 m field sits inside the 6 m face with 1.4 m spare at each end, which keeps the readout off the two ways a face receiver lies: it saturates at 1.0 for about 20 mm past the face plane, and past that reads exactly 0 — the same value as "nothing overlaps".

**Rotation without trig or physbones** (mechanism — two markers on orthogonal arms, a `VRCAimConstraint` pair rebuilding orientation — in `generate.py`'s docstring). One trap it names and this repeats because it costs a session: `Recon`'s `WorldUpType` must be **ObjectRotationUp**; `ObjectUp` looks like the right token and silently degenerates to world up, never correct here. The `y` preset sends marker components rather than a heading because a parameter driver reads 0 from an AAP, so no walk can quantize a number a blend tree computed — and its two components are not two values but one heading, both halves of which (sample and publish) need a single frame. One **serial pair layer** owns that: its `Start` driver copies both residuals in one frame, the A/X ladder walks its frozen residual and steps straight into the A/Z ladder, and one commit publishes all 24 bits — so the committed pair is an angle the marker actually held at some instant, whatever the yaw rate. Serializing costs nothing in cycle time. Full mode's six components are independent readings, so a torn set is a stale orientation rather than one no marker held.

**The wire, and why nothing tears.** Each axis's coarse byte, fine byte and eight bools share one `group:`, so word-channel batches them and `atomic: batch` applies them together — an adjacent-cell coarse always lands with its matched fine, so cell-boundary flicker needs no hysteresis. The walks are multi-frame and safe (they run only on the wearer's own client, which cannot cull itself), but the handoff must not be — word-channel's sender copies word params on its own clock and would latch a half-written axis — so the walks fill scratch staging and one `Commit` state driver-copies a whole axis in a single frame (`generate.py`'s docstring: the producer is multi-frame, the commit is not).

**The decode reads one-frame-old copies of every word limb, bytes included — and the bytes are the load-bearing half.** A `Floatify` driver mirrors the word bools into float scratch one frame late; the byte words are already tree-readable, and reading them raw is a measured defect — byte on the direct path, bool tail on the copy path, so the assembled `D/…` pair mixes new and stale for one frame on every coarse-word change. Measured on emulator and shipping client (13-bit geometry, bit-width-independent, the 12+12 tail capping the excursion at ±15 cells): a one-frame excursion of exactly one cell (2.0 m) per cell crossing, and ±62 m where the crossing lands on a coarse byte boundary — which reads in game as the prop vanishing for a frame and a consumer's damper integrates into a lurch. The fix is routing the bytes through the same `Floatify` copy; nothing asserts it, so the fast path can creep back and review is the only guard.

**Who drives the prop is a latch, not a predicate held both ways.** The `Follow` layer engages the reconstruction on `!IsLocal AND ObjectSync/Enable AND OS/Ready` and exits on `Enable` alone, so once engaged it holds through whatever `Ready` does after — a receiver falling to `Lost` mid-session does not drop the prop. **Add a rung here without deciding what it does to that latch, and you un-latch it.** The `Ready` term is the late-joiner gate: a fresh clone's table is all zeros, zero is cell 0, cell 0 is the range corner, so engaging before a whole table arrives would show the corner. It is the `Floatify` copy and not raw `OSCh/Acquired`, which the receiver certifies one frame before those words reach the decode. The wearer's copy never rides the decode — it moves under the consumer's own system, no constraint of ours between the carry constraint and the prop.

**The enable, and what it does not gate.** Off, a 1D tree on `ObjectSync/Enable` deactivates the three measure subtrees, and each layer clears its staging, residual, cell index and sense params *in that order* — because a deactivated sensing component does not fall to zero, it freezes at its last reading, and only a clear written after the deactivation sticks. Enable does **not** gate the wire (word-channel's 27 bits are allocated regardless, so gating would save nothing and cost a full re-lock), and the word table is left holding the last committed pose so re-enabling shows the prop where it was. Consequence: the receiver keeps decoding through the toggle, so `OS/Ready` stays true across an Enable-off and flipping it back on engages on that frame rather than waiting out a cycle.

**Coming back up is where a clear turns into a lie.** A cleared sense param reads 0, and 0 quantizes to cell 0 — the range corner — so a walk sampling before its reactivated receivers re-acquire publishes a confident wrong answer. Walks therefore gate on **receiver liveness, not a timer**: a 0 reading is never legal in-volume (the edge guard's second job), and each walk-entry transition requires the params it is about to sample to read above a guard-derived threshold. Re-acquisition measured 7 frames in the emulator, is unbounded in principle, and the gate does not care. The multi-object `Slice` layer is the same discipline per slice, with a bounded skip so a rig that never wakes yields its slice, and an abandon rung so a walk that loses its rig mid-flight does not commit limbs measured against another object's senders — that hand-off gates on the walks' own `Slice/Done` stamps, not a wall-clock dwell, because at any rate where a fixed Run window stops fitting the abandon rung beheads the slowest walk each cycle. **Position words frozen at zero under a live, replicating heading is that defect's exact fingerprint** (every decoded prop parks at the range corner, kilometres out). The wall-clock escape survives only as the yield bound on a slice that cannot finish, sized at CONFIG's `sliceFloorFps`.

**A gate is only safe where waiting can end.** One liveness wait fails that: the fine receiver rides the measurement anchor, which only a fresh coarse commit moves, so a teleport out of the current cell while the walk is past the coarse stage strands the fine sender outside its box — measured as 2 of 5 instantaneous teleports stalling the position stage indefinitely while rotation, whose markers cannot leave their boxes, kept tracking. The fine wait therefore carries the one escape: after `fineEscapeFrames` of dead reading it abandons to `Idle`, restages the cell and restores overlap. Every other wait is on a self-restoring source, and `generate.py`'s liveness audit records which is which, unasserted — so a new gate added without an entry saying why its waiting ends passes every check.

**Empirical constants** (measured in the emulator; re-measure before changing any of them):

| Constant | Value | Where it lands |
|---|---|---|
| Coarse readout error, contact space | 0.39 mm worst case, measured with the avatar up to 8 km from world origin (a bound with margin inside the ±4096 m volume) | `coarseNoise` in CONFIG; amplified by `range/coarseHalfSpan` to 0.58 m of world error, and the fine field is widened by twice the 0.60 m guard that ceilings it |

| Fine-anchor settle | 1 frame to the cell centre, 2–4 frames to a coherent reading | `settleFrames` = 4 |

**Costs.** **370 states and 14 layers** for the root build (248/9 and 269/10 for `y` and `y_double`); the generator's compile line prints each variant's counts. 33 frames (~0.55 s) per local measure cycle plus receiver settle, ~0.70 s per wire refresh, ~1.3 s worst case end to end. A multi-object build costs a slice per ring slot, ~0.8 s per slice — the shared walk set is why N objects cost walk states once, not N times. Twelve local-only receivers per full-rotation object, eight per y object, zero physbones; the `Floatify` driver copies every word limb plus `Acquired` every frame on every client (60+1 params for the root build) — one driver however many objects, the term that scales worst with N. Speed ceiling: sustained authority motion faster than roughly the fine field over one measure-plus-wire interval (≈ 5–6 m/s at 60 fps for the committed single-object geometry) walks the fine sender out of its box every cycle, so the escape restages continuously and the display holds the last good commit. A droppable prop never reaches it; a projectile is out of scope by construction. Packing, commit reachability, the liveness gate on every walk entry, the slice sequencing, the reconstruction shapes, and the rule that no driver reads or writes an AAP param are all unasserted — the last is the defect that cost y-mode its first design, and only review catches it.

## Verifying the install

Cheapest observable: **move `Sync_Target` with the wearer standing away from the world origin and facing away from +Z**. On the wearer, `Sync` must track it frame-for-frame; any lag there means the local branch is riding something it must not. On a remote clone, `Sync` reaches the same world pose inside about a second — millimetres of position, hundredths of a degree of rotation, the same value on both sides because both decode the same words — and the build's `OS/Ready` (instance-prefixed post-bake: `VF##_OS/Ready`) must be true on that clone. The off-origin, off-axis stance is the part that is easy to skip and the part that catches the whole class: a rig frame that has quietly stayed avatar-relative is indistinguishable from a correct one at the origin, so read `Rig` while you are there and require exactly `(0, 0, 0)` with identity rotation on both clients, with `Rig/Prop` at exactly `(73, 932, 233)` and the pin's source offset zero — and lossy scale exactly `(1, 1, 1)` with the avatar scaled away from upload height (av3emu: `EnableAvatarScaling` + `AvatarHeight` on the local runtime), which is the check that catches a lost scale pin: unpinned, the fine receivers read exactly 0 past the Rig table's `|scale−1| > 0.0013` bound while coarse and rotation stay green, the same verdict a world eye-height clamp produces in game. Local and clone disagreeing by more than quantization is the decode reading a different word table, not the wire being slow; a clone's `Sync` frozen while `VF##_OS/Ch/Cycle` climbs is the rig rather than the wire (`../word-channel`'s own §Verifying owns that reading, and why the counter carries a per-build instance prefix). On a cold join `OS/Ready` is false and the prop rides `Sync_Target` for **one to two loops (~0.7–1.4 s)** before the reconstruction takes over already at its synced pose — a late joiner never sees the range corner at all. **The spread is the normal reading, not a fault**: under `atomic: batch` the receiver re-locks at any counter value, and only a join landing on a batch head certifies at that loop's tail. For the drop path: with a hand source on `Sync_Target` and Enable on, Drop-on must freeze the wearer's prop on that frame and walk a clone to the same world pose inside the usual ~1.3 s; Drop-off must snap the wearer's prop back to the hand on that frame — any wearer-side lag on either edge means something other than `FreezeToWorld` is in the local path.

Two more reads on a multi-object build, both cheap in the same session. **The shared sense params across a slice boundary**: exactly one nonzero writer at any moment, exactly 0 through an Enter's clear gap, and no reading surviving from the outgoing object into the incoming object's walk entry — the Enter clear plus the liveness gates are what stand between a graceful wait and a cross-object publish, so a stale value here is the highest-severity fault this rework can have. **A y object under continuous yaw**: every committed heading pair must reconstruct an angle the marker actually held at some instant — a commit mixing two sample times reads as a heading sweeping THROUGH angles the prop never faced, and the pair layer's single-frame sampling exists precisely so that cannot happen.

What the emulator structurally cannot show for this entry: everything `../word-channel` declares — its wire is this entry's wire — plus four that belong to the measure rig. **Contacts are never simulated against a remote clone**, so the twelve receivers are only ever exercised on the wearer's own client, and nothing here can reach a fault that needs another player's dynamics to appear — which is also why the park is an argument rather than a measurement: `(73, 932, 233)` is empty in a test scene by construction, where a real world may put geometry or another player's props through it. And **contact re-registration latency is the emulator's, not the client's**: a reactivated receiver takes 7 frames here, the shipping client is unmeasured, and the design gates on the reading rather than on that number precisely so the difference cannot matter. **Contact readout temporal noise is the client's, not the emulator's** — present at rest, amplified by wearer motion. The emulator's sense values are bit-constant frozen-and-stationary at every range (measured 0–8 km); the client's jitter continuously even at rest — about a tenth of a cell of span at 1000 m over a ~30 s window, a margin, not a guarantee: no word change was observed, but a pose parked close enough to a cell boundary still can commit. It is *wearer motion* that swings the readout of a world-frozen target to a full cell of span at 1000 m, dithering the committed coarse word at roughly one event per second (measured in-client under desktop movement). Distinguish that from the constants table's 0.39 mm coarse error, which is a static position-dependent bias both venues share. A dithered pair still reconstructs the true position — the redundant fine field absorbs an off-by-one cell by design — so at the measured range the dither costs accuracy nothing and matters only as extra coarse-word events, each of which the decode must (and, since the shared `Floatify` copy, does) apply coherently. That free-ness is bounded, not structural: the motion swing is ±0.52 m of world equivalent at 1000 m (the squeeze scales it with `range/coarseHalfSpan`, so the measured 13-bit figure halves at this geometry) against the fine field's ±0.60 m coarse guard — the same ~13% headroom — and the guard was sized for the static at-range bias this term adds to, so past 1000 m, where the swing is unmeasured and scales with distance, the off-by-one absorption is not known to hold. A fourth gap is the one the zero-offset pin closes: **the emulator SDK never scales a constraint source's offset by avatar scale, so a park that crept back onto any source offset would pass every emulator check and still misplace the prop cross-client.** The emulator-expressible shadow is the injected-scaling fixture: in play mode, apply the client's rule by hand — multiply every source offset on the remote clone's root pin constraints by a forced-scale factor (×1.35, say) — and require local/clone `Sync` agreement unchanged, which holds exactly when every offset is zero; injecting a park-sized offset first and watching agreement break by that vector is the teeth check. No committed prefab carries a nonzero source offset; run `generate.py --check`. The document's animated source-space offsets are unasserted, and only an in-client two-scale read (`../../docs/runtime.md` §Constraints) sees the real client behavior.
